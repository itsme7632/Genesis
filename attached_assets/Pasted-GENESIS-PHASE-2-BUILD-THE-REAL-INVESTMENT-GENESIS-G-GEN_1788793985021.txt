==================================================

==================================================
6. BALANCE HANDLING
==================================================

When an investment is created:

Use a database transaction.

Validate the user's available wallet balance.

Then:

1. Lock/deduct the investment amount according to the configured investment model.
2. Create the Investment record.
3. Create the corresponding Transaction record.
4. Record the event in an auditable way.
5. Commit everything atomically.

If any operation fails:

ROLL BACK EVERYTHING.

Never create an investment without the corresponding balance change.

Never deduct balance without creating the corresponding investment/transaction.

8. G GENERATION ENGINE
==================================================

The system must NOT have:

- Reward rate
- Reward frequency
- Investment start time
- Current time
- Applicable terms
- Any configured caps/limits if implemented

Create auditable G generation events.

Use the existing GReward and GGenerationEvent models.

==================================================
9. EXAMPLE G CALCULATION
==================================================

For a simple daily percentage reward model:

Investment amount:
500 USDT

Configured reward rate:
1.5% daily

Daily reward value:
500 × 0.015 = 7.50 USDT-equivalent reward value per day

The actual number of G credited must be determined from the configured G valuation/reference price or reward conversion rules.

For example, if the current configured G reference price is:

$0.10 per G

then:

$7.50 reward value ÷ $0.10 = 75 G

IMPORTANT:

Do not assume this exact conversion model is permanently correct.

Build the system so Admin can control/configure the reward methodology.

At minimum, separate:

1. Investment reward value calculation
2. Conversion of reward value into G

This is important because G will eventually have a real market price after launch.

==================================================
11. G REWARD ACCOUNTING
==================================================

G rewards must be persistent.

Each reward event should contain enough information to audit the calculation.

For example:

- userId
- investmentId
- reward asset
- reward amount
- reward value
- G price used
- G amount credited
- calculation period
- createdAt
- source
- status

Do not create duplicate rewards if the same calculation period is processed twice.

Reward generation must be idempotent.

If the reward engine runs again for an already-accounted period, it must not double-credit the user.

==================================================
12. HOW REWARDS SHOULD BE ACCRUED
==================================================

Build a backend reward-accrual service.

The preferred architecture is:

CALCULATE FROM ELAPSED TIME

rather than requiring the server to execute a reward event every second.

For example:

Investment started:
September 7 at 10:00

Current time:
September 8 at 10:00

Elapsed:
24 hours

Calculate the amount earned based on the configured daily rate.

When the user opens Portfolio, the backend can calculate/account for the accrued reward.

Also prepare the architecture for a scheduled/background reward processor later.

The important requirement:

The balance must be derived from authoritative backend calculations.
